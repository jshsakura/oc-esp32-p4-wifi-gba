# GLM 레인 — PC Engine이 왜 31fps인가 (2026-08-04)

## 맡을 것

**PC Engine이 31.1fps로 돈다. 2026-08-02에는 58-60fps였다.** 그런데 BUSY가 17~21%뿐이다
— CPU가 모자란 게 아니라 **뭔가가 프레임을 절반으로 페이싱하고 있다.**

측정값 (고친 스윕, 부팅 배너·롬 경로 확인됨):

    pce   31.1 fps   BUSY 17.4%   5,593 us/frame

BUSY 17%면 프레임당 5.6ms만 쓰고 나머지를 논다는 뜻이다. 60fps면 예산이 16.7ms다.
**여유가 3배 있는데 31fps다.** 원인은 에뮬레이션 비용이 아니다.

## 어디부터 볼 것

- `retro-core/main/main_pce.c` — `rg_system_set_tick_rate()`에 뭘 넣는지. 다른 코어와
  비교할 것: `main_sms.c:160`은 `(sms.display == DISPLAY_NTSC) ? FPS_NTSC : FPS_PAL`로
  고른다. pce가 PAL 값이나 절반 값을 쓰고 있지 않은지.
- `app->frameskip` 경로. 프레임을 버리면 fps는 떨어지고 BUSY도 같이 떨어진다.
- `rg_display_submit()` 호출 빈도 — 한 프레임 걸러 내고 있지 않은지.

## 재현

    python3 tools/sweep_systems.py pce

빌드·플래시·부팅·캡처를 다 한다. 로그는 `/tmp/rg_sweep/pce.log`.

## 지켜야 할 것

- **`retro-core`만 건드린다.** `sm-go`는 지금 다른 세션이 붙어 있다. 두 세션이 같은 앱을
  빌드하면 `rg_tool.py`가 서로의 `build/`를 지운다.
- **시리얼 포트(`/dev/ttyACM0`)는 지금 다른 세션이 쓰고 있다.** 코드 읽고 고치고 빌드까지
  하고, **기기에 올리기 전에 물어볼 것.** 스윕을 그냥 돌리면 남의 측정을 망친다.
- **`tools/sweep_systems.py`를 고치지 말 것.** 오늘 대대적으로 고쳤다.
- 숫자는 `us/frame`으로 말할 것. BUSY%는 발열로 흐른다.
- **모르겠으면 스텁 만들지 말고 멈추고 보고할 것.** 추측으로 tick rate를 바꿔놓으면
  다음 사람이 왜 그런지 알 수 없다.
